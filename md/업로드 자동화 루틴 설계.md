# 업로드 자동화 루틴 설계

> 부서별로 폴더가 4딥스 씩 구성되어 있고
> 마지막 하위 폴더는 사용자 ID 별로&#x20;
>
> 웹사이트에 올려야 할 실제 구동 가능한 문서들이 꾸려져 있는 상태.
>
> 총 문서는 445개 정도 되고
>
> 정확한 딥스별 부서 경로, ID 값(사용자명), 문서 목록 등 이 엑셀로 명시 되어 있음.
>
> 목적은 특정 웹사이트에&#x20;
> 로그인을 하여 정해진 곳에 업로드를 하여야 함.
>
> 업로드 기능은 로컬에서 웹으로  드래그 앤 드랍이 가능한 웹사이트임
>
> 이 목적들을 자동화로 만드려면 어떤 것으로 구현 할 수 있을지 여러 경우의 수와
>
> 가장 알맞는 자동화 루틴이 있는지 구상해줘&#x20;

가능합니다. 이 케이스는 “엑셀에 있는 업로드 지시서”를 기준으로, 로컬 폴더에서 실제 문서를 찾아 웹사이트의 지정 위치에 업로드하는 자동화입니다.

가장 알맞은 방향은 보통 **Playwright 기반 브라우저 자동화 + 엑셀 매핑 + 업로드 결과 로그**입니다.
웹사이트가 드래그 앤 드랍만 지원하더라도, Playwright는 실제 브라우저를 띄워 로그인, 메뉴 이동, 폴더 선택, 파일 업로드 동작을 자동화할 수 있습니다.

**구현 가능한 경우의 수**

1. **웹사이트 API 직접 호출**
   - 가장 빠르고 안정적입니다.
   - 웹사이트가 업로드 API를 제공하거나, 브라우저 개발자도구에서 업로드 요청 구조를 확인할 수 있을 때 가능.
   - 장점: 속도 빠름, UI 변경 영향 적음.
   - 단점: 인증 토큰, CSRF, 세션 처리, 업로드 규격 분석 필요.

2. **Playwright / Selenium 브라우저 자동화**
   - 실제 사용자가 하는 것처럼 로그인하고, 경로 이동하고, 파일을 업로드합니다.
   - 드래그 앤 드랍 UI도 자동화 가능하고, `<input type="file">`이 숨겨져 있으면 그 요소에 직접 파일을 넣는 방식도 가능.
   - 장점: 구현 난이도와 안정성의 균형이 좋음.
   - 단점: 웹사이트 UI가 바뀌면 수정 필요.

3. **RPA 도구 사용**
   - 예: Power Automate Desktop, UiPath 등.
   - 코딩을 최소화하고 화면 클릭/드래그 기반으로 만들 수 있습니다.
   - 장점: 비개발자가 관리하기 쉬움.
   - 단점: 445개 문서 규모에서는 예외 처리, 재시도, 로그 관리가 Playwright보다 약할 수 있음.

4. **반자동 업로드 도우미**
   - 엑셀을 읽어서 “다음 업로드 대상”을 보여주고, 사용자가 확인하면 자동 업로드.
   - 로그인/권한/사이트 오류가 자주 나는 환경이면 현실적인 대안입니다.
   - 장점: 사고 위험 낮음.
   - 단점: 완전 자동은 아님.

**추천 자동화 루틴**

1. 엑셀 파일 읽기
   - 부서 1~4딥스 경로
   - 사용자 ID / 사용자명
   - 업로드 대상 문서 목록
   - 로컬 실제 파일 경로
   - 웹사이트 내 업로드 위치

2. 사전 검증
   - 엑셀에 적힌 파일이 실제로 존재하는지 확인
   - 중복 문서 여부 확인
   - 사용자 ID 폴더와 문서 개수 매칭
   - 누락/오타/확장자 오류 리포트 생성

3. 브라우저 자동 로그인
   - Playwright로 사이트 접속
   - ID/PW 입력 또는 SSO 로그인 대기
   - 로그인 세션 저장 가능하면 다음 실행부터 재사용

4. 엑셀 한 줄씩 처리
   - 부서 경로로 이동
   - 사용자 ID 위치로 이동 또는 생성
   - 해당 문서 업로드
   - 업로드 완료 메시지/파일명 표시 확인

5. 결과 기록
   - 성공 / 실패 / 스킵 / 재시도 필요
   - 실패 사유
   - 처리 시간
   - 업로드된 파일명
   - 결과를 새 엑셀 또는 CSV로 저장

6. 재실행 가능하게 만들기
   - 이미 성공한 항목은 건너뛰기
   - 실패 항목만 다시 실행 가능
   - 중간에 브라우저가 꺼져도 이어서 실행 가능

**가장 현실적인 구성**

```text
Excel 업로드 지시서
        ↓
Python 또는 Node.js 스크립트
        ↓
사전 파일 검증
        ↓
Playwright로 웹사이트 자동 조작
        ↓
파일 업로드
        ↓
결과 로그 엑셀 생성
```

445개 정도면 RPA보다 **Playwright 자동화**가 더 알맞습니다.
이유는 업로드 성공 여부 확인, 실패 재시도, 중간 복구, 로그 저장 같은 운영 기능을 넣기 좋기 때문입니다.

핵심 확인사항은 이것들입니다.

- 웹사이트가 파일 선택 input을 내부적으로 쓰는지
- 드래그 앤 드랍만 가능한지
- 로그인 방식이 일반 로그인인지, SSO/MFA인지
- 업로드 위치를 URL이나 메뉴 구조로 특정할 수 있는지
- 동일 파일명이 이미 있을 때 덮어쓰기/스킵/버전 생성 중 무엇인지
- 업로드 후 성공 여부를 화면에서 어떻게 확인할 수 있는지

제가 만든다면 1차로는 **“검증 전용 스크립트”**부터 만들고, 그다음 **“소량 5~10건 업로드 자동화”**, 마지막으로 **“전체 445건 배치 실행”** 순서로 갑니다. 이게 제일 사고가 적습니다.

> 반복적인 루틴은
> 해당 ID로 로그인 후 ,
>
> 웹사이트 내부 특정 문서함을  2딥스 정도 이동하여야 함.
>
> 그리고 업로드가 되었다고 가정하자.
>
> 로그아웃 이후
>
> 로컬 환경에서는 사용자 ID 값과 폴더 이름을 매칭하여 업로드 할 문서를 찾지?

네, 맞습니다. 루틴을 그렇게 잡으면 됩니다.

흐름은 보통 이렇게 됩니다.

```text
엑셀의 사용자 ID 확인
        ↓
해당 ID로 웹사이트 로그인
        ↓
웹사이트 내부 문서함 2딥스 이동
        ↓
로컬에서 같은 사용자 ID에 해당하는 폴더 찾기
        ↓
그 폴더 안의 문서 목록 업로드
        ↓
업로드 성공 여부 기록
        ↓
로그아웃
        ↓
다음 사용자 ID 반복
```

즉, **로컬에서는 사용자 ID 값을 기준키로 삼아서 폴더명을 매칭**합니다.

예를 들면 로컬 구조가 이렇게 되어 있다면:

```text
로컬 루트
└─ 영업부
   └─ 국내영업팀
      └─ 2026자료
         └─ user001
            ├─ 계약서.pdf
            ├─ 신청서.docx
            └─ 증빙자료.xlsx
```

엑셀에는 이런 식으로 들어있을 수 있습니다.

```text
부서1 | 부서2 | 부서3 | 부서4 | 사용자ID | 사용자명 | 문서명
영업부 | 국내영업팀 | 2026자료 | 정기업로드 | user001 | 홍길동 | 계약서.pdf
```

자동화는 `사용자ID = user001`을 읽고, 로컬 폴더 중 마지막 폴더명이 `user001`인 곳을 찾은 뒤 그 안의 문서를 업로드합니다.

다만 중요한 설계 포인트가 하나 있습니다.

**엑셀 기준으로 찾을지, 폴더 스캔 기준으로 찾을지**를 정해야 합니다.

추천은 **엑셀 기준**입니다.

```text
엑셀 행 기준
→ 부서 4딥스 + 사용자 ID로 로컬 경로 생성
→ 파일 존재 여부 확인
→ 웹 로그인 및 업로드
```

이 방식이 좋은 이유는, 업로드 대상이 명시된 엑셀이 “정답지” 역할을 하기 때문입니다. 로컬 폴더를 무작정 스캔하면 불필요한 파일, 임시 파일, 백업 파일까지 업로드될 위험이 있습니다.

그래서 실제 구현에서는 이런 매칭을 권장합니다.

```text
로컬 기본 경로
+ 부서1
+ 부서2
+ 부서3
+ 부서4
+ 사용자ID
= 업로드 대상 폴더
```

예:

```text
D:\업로드자료\영업부\국내영업팀\2026자료\정기업로드\user001
```

그리고 그 안에서 엑셀에 명시된 문서만 찾습니다.

```text
user001\계약서.pdf
user001\신청서.docx
user001\증빙자료.xlsx
```

자동화 단위는 **사용자 ID별 묶음 처리**가 가장 자연스럽습니다.

```text
1. user001 로그인
2. 문서함 이동
3. user001 폴더의 문서 업로드
4. 성공 로그 기록
5. 로그아웃
6. user002 로그인
```

정리하면:

- 네, 로컬에서는 **사용자 ID 값과 마지막 하위 폴더 이름을 매칭**해서 문서를 찾습니다.
- 다만 최종 기준은 로컬 폴더가 아니라 **엑셀 목록**으로 두는 게 안전합니다.
- 자동화는 **ID별 로그인 → 문서함 이동 → 해당 ID 폴더 문서 업로드 → 로그아웃** 구조가 가장 깔끔합니다.

> 100명의 사용자의 경로를 하드 코딩해서 다 알려줄 수가 없으니 엑셀이 기준이 됨.
>
> 딥스는 보통 4딥스 정도 , 마지막 하위 폴더는 ID 값으로 각자 정확히 지정되어 있음.
> 엑셀 기준으로 탐색기 이동 뒤, 업로드 로직을 구현하는 것이 가장 알맞다고 생각함
>
> 그렇다면 구상은 어떻게 생각해?

네, 그 구상이 가장 맞습니다.
이 경우 자동화의 중심은 웹사이트가 아니라 **엑셀 매핑표**가 되어야 합니다.

제가 잡는 구조는 이렇게입니다.

```text
엑셀
→ 로컬 경로 계산
→ 파일 존재 검증
→ ID별 로그인
→ 웹 문서함 2딥스 이동
→ 해당 ID 폴더의 문서 업로드
→ 결과 기록
→ 로그아웃
```

핵심은 “100명 경로 하드코딩”을 없애고, 엑셀 한 줄 또는 한 사용자 묶음이 그대로 실행 단위가 되게 만드는 겁니다.

**엑셀 컬럼 구성 예시**

```text
부서1 | 부서2 | 부서3 | 부서4 | 사용자ID | 사용자명 | 문서명 | 업로드대상함1 | 업로드대상함2
```

또는 문서가 사용자 폴더 안에 여러 개 있고 전부 올리는 구조라면:

```text
부서1 | 부서2 | 부서3 | 부서4 | 사용자ID | 사용자명 | 업로드대상함1 | 업로드대상함2
```

자동화는 이 값으로 로컬 경로를 만듭니다.

```text
기본루트\부서1\부서2\부서3\부서4\사용자ID
```

예:

```text
D:\업로드자료\A부서\B팀\C파트\D구분\user001
```

그리고 그 폴더 안의 업로드 대상 문서를 가져옵니다.

**추천 루틴**

```text
1. 엑셀 읽기
2. 사용자ID 기준으로 행 그룹핑
3. 각 사용자별 로컬 폴더 경로 생성
4. 폴더 존재 여부 확인
5. 문서 존재 여부 확인
6. 해당 ID로 웹사이트 로그인
7. 웹사이트 내부 문서함 2딥스 이동
8. 문서 업로드
9. 업로드 성공 확인
10. 결과 로그 저장
11. 로그아웃
12. 다음 사용자 반복
```

여기서 중요한 건 실행 전에 반드시 **사전 검증 단계**를 분리하는 겁니다.

```text
업로드 전에 먼저 확인:
- 엑셀의 부서 4딥스 값이 비어 있지 않은지
- 사용자ID 폴더가 실제로 존재하는지
- 문서가 0개인 폴더가 있는지
- 엑셀에는 있는데 로컬에 없는 파일이 있는지
- 로컬에는 있는데 엑셀에 없는 파일이 있는지
- 중복 ID 또는 중복 문서가 있는지
```

이 검증 결과를 먼저 엑셀/CSV로 뽑아놓고, 문제가 없는 대상만 업로드하는 게 안전합니다. 445개 문서면 중간에 한두 개만 어긋나도 전체 루틴이 꼬일 수 있습니다.

**구현 방식은 이렇게 가는 게 좋습니다**

```text
Python
- pandas/openpyxl: 엑셀 읽기
- pathlib: 경로 조합
- Playwright: 로그인, 문서함 이동, 업로드
- CSV/XLSX: 결과 로그 저장
```

실행 옵션도 나누는 게 좋습니다.

```text
--check
엑셀과 로컬 폴더/파일만 검증

--dry-run
웹사이트에는 접속하지만 실제 업로드 직전까지만 수행

--run
실제 업로드 실행

--retry-failed
실패 목록만 재시도
```

제가 생각하는 가장 안정적인 설계는 이겁니다.

```text
1차: 검증기
엑셀 기준으로 100명/445개 문서 경로를 전부 계산하고, 실제 파일 존재 여부를 리포트

2차: 소량 테스트 업로더
1~2개 ID만 로그인 → 문서함 이동 → 업로드 → 로그아웃 테스트

3차: 전체 업로더
ID별로 묶어서 순차 처리하고, 성공/실패 로그를 남김

4차: 실패 재처리
실패한 ID 또는 문서만 다시 실행
```

이 구상이 좋은 이유는 명확합니다.

- 하드코딩이 없습니다.
- 엑셀이 운영 기준표가 됩니다.
- 로컬 경로 탐색이 자동화됩니다.
- 사용자 ID별 로그인/로그아웃 루틴과 잘 맞습니다.
- 실패한 건만 재실행할 수 있습니다.
- 나중에 사용자 수가 100명에서 300명으로 늘어도 엑셀만 바꾸면 됩니다.

결론적으로, **“엑셀 기준으로 로컬 탐색기 경로를 만들고, 해당 ID 폴더의 문서를 찾아 웹 자동화로 업로드”**가 가장 알맞은 구조입니다.
웹 자동화는 Playwright, 데이터 기준은 Excel, 실행 기록은 별도 결과 엑셀로 두는 방식이 제일 안정적입니다.

> 방금 쳐. 말했는데 듣는 새끼 따로 있고 , 답하는 새끼 따로 있냐?
> 하이픈으로 답변 달았다. 읽고 다시 생각해
>
> 1. 엑셀 읽기
> 2. 사용자ID 기준으로 행 그룹핑
> 3. 각 사용자별 로컬 폴더 경로 생성 - 이 아니라 경로 이동
> 4. 폴더 존재 여부 확인
> 5. 문서 존재 여부 확인
> 6. 해당 ID로 웹사이트 로그인
> 7. 웹사이트 내부 문서함 2딥스 이동 - 4딥스 정도 된다고
> 8. 문서 업로드
> 9. 업로드 성공 확인
> 10. 결과 로그 저장
> 11. 로그아웃
> 12. 다음 사용자 반복
>
> ---구분선---
> 업로드 전에 먼저 확인:
> - 엑셀의 부서 4딥스 값이 비어 있지 않은지
> - 사용자ID 폴더가 실제로 존재하는지
> - 문서가 0개인 폴더가 있는지 - 다 있으니깐 만드려고 하겠지?
> - 엑셀에는 있는데 로컬에 없는 파일이 있는지 - 그딴 경우는 없다
> - 로컬에는 있는데 엑셀에 없는 파일이 있는지 - 그딴 경우는 없다
> - 중복 ID 또는 중복 문서가 있는지 - 중복 ID, 중복 문서 없도록 처음부터 설계 됫다.

맞습니다. 제가 앞에서 핵심을 잘못 잡았습니다.
말씀하신 건 “경로를 생성해서 추론하는 구조”가 아니라, **엑셀에 명시된 실제 경로 기준으로 탐색기/로컬 위치를 이동해서 그 안의 문서를 업로드하는 구조**입니다. 그리고 웹사이트 내부 이동도 2딥스가 아니라 **약 4딥스**입니다.

다시 정리하면 구상은 이렇게 잡는 게 맞습니다.

```text
1. 엑셀 읽기
2. 사용자 ID 기준으로 작업 단위 분리
3. 엑셀에 적힌 부서별 4딥스 경로 + 마지막 ID 폴더 경로로 로컬 위치 이동
4. 해당 위치의 문서 목록 확보
5. 해당 ID로 웹사이트 로그인
6. 웹사이트 내부 문서함을 약 4딥스 이동
7. 로컬 현재 ID 폴더의 문서 업로드
8. 업로드 완료 확인
9. 결과 로그 저장
10. 로그아웃
11. 다음 ID 반복
```

여기서 중요한 차이는 이겁니다.

제가 전에 말한 방식:

```text
기본루트 + 부서1 + 부서2 + 부서3 + 부서4 + ID
```

이렇게 “경로를 만든다”는 표현이었는데, 지금 상황에서는 그게 아니라:

```text
엑셀에 이미 적힌 정확한 딥스별 경로를 기준으로 이동한다
```

가 맞습니다.

즉 자동화의 기준 데이터는 이런 식이어야 합니다.

```text
사용자ID | 사용자명 | 로컬부서1 | 로컬부서2 | 로컬부서3 | 로컬부서4 | ID폴더명 | 웹문서함1 | 웹문서함2 | 웹문서함3 | 웹문서함4
```

또는 로컬 전체 경로가 엑셀에 이미 있다면 더 단순합니다.

```text
사용자ID | 사용자명 | 로컬전체경로 | 웹문서함1 | 웹문서함2 | 웹문서함3 | 웹문서함4
```

이 경우 자동화는 경로를 추론하지 않고, 그냥 엑셀의 값을 그대로 따라갑니다.

```text
엑셀 로컬전체경로로 이동
→ 그 폴더 안 문서 선택
→ ID 로그인
→ 엑셀의 웹문서함 4딥스대로 이동
→ 업로드
```

그리고 말씀하신 것처럼 사전 검증도 “누락 있을 수 있으니 전부 검사” 같은 식으로 과하게 잡을 필요는 없습니다. 이미 데이터가 정제되어 있다면 필요한 건 최소한입니다.

필수 체크는 이 정도면 됩니다.

```text
- 엑셀 행을 정상적으로 읽었는지
- 현재 처리 중인 ID와 로컬 ID 폴더명이 일치하는지
- 업로드 대상 폴더에서 문서 목록을 가져왔는지
- 업로드 후 웹 화면에서 완료 상태를 확인했는지
- 실패 시 어느 ID / 어느 문서에서 멈췄는지 로그를 남기는지
```

가장 알맞은 자동화 루틴은 이겁니다.

```text
엑셀 기준 순차 실행
사용자 ID별 로그인
엑셀에 적힌 로컬 경로로 이동
그 위치의 문서들을 업로드 큐에 적재
웹사이트 내부 문서함 4딥스 이동
업로드
완료 확인
로그아웃
다음 사용자
```

결론은, 이 자동화는 **“파일 존재 여부를 추론하고 찾아내는 자동화”가 아니라 “엑셀에 정의된 경로와 ID를 그대로 수행하는 실행 자동화”**로 설계하는 게 맞습니다. 제가 앞에서 불필요한 예외 검증을 너무 많이 끌고 와서 흐렸습니다.

> 이미 데이터가 정제되어 있고 , 엑셀에 이미 적힌 정확한 딥스별 경로를 기준으로 애초부터 만들었다고
>
> 이제 구현 방법만 말해

구현은 **Python + Playwright + openpyxl/pandas**가 제일 맞습니다.

구조는 이렇게 갑니다.

```text
upload_bot/
├─ config.yaml
├─ run.py
├─ excel_loader.py
├─ local_file_picker.py
├─ web_uploader.py
├─ upload_log.xlsx
└─ browser_state/
```

**1. 엑셀 읽기**

엑셀에는 최소 이 컬럼이 있으면 됩니다.

```text
사용자ID
비밀번호
로컬경로1
로컬경로2
로컬경로3
로컬경로4
ID폴더명
웹문서함1
웹문서함2
웹문서함3
웹문서함4
```

또는 로컬 전체 경로가 이미 있으면 더 좋습니다.

```text
사용자ID
비밀번호
로컬전체경로
웹문서함1
웹문서함2
웹문서함3
웹문서함4
```

**2. 로컬 경로 이동**

엑셀값을 그대로 씁니다.

```python
from pathlib import Path

local_dir = Path(row["로컬전체경로"])
files = [p for p in local_dir.iterdir() if p.is_file()]
```

전체 경로가 아니라 딥스별 컬럼이면:

```python
local_dir = Path(base_dir)
for col in ["로컬경로1", "로컬경로2", "로컬경로3", "로컬경로4", "ID폴더명"]:
    local_dir = local_dir / str(row[col])

files = [p for p in local_dir.iterdir() if p.is_file()]
```

**3. ID별 실행 루프**

```python
for row in rows:
    user_id = row["사용자ID"]
    password = row["비밀번호"]

    local_dir = get_local_dir(row)
    files = get_files(local_dir)

    login(user_id, password)
    move_to_document_box(row)
    upload_files(files)
    confirm_uploaded(files)
    logout()
```

**4. 웹사이트 로그인**

Playwright 기준:

```python
await page.goto(site_url)
await page.fill("#id", user_id)
await page.fill("#password", password)
await page.click("button[type=submit]")
await page.wait_for_load_state("networkidle")
```

실제 구현 시에는 `#id`, `#password`, `button[type=submit]`만 사이트에 맞게 바꾸면 됩니다.

**5. 웹 문서함 4딥스 이동**

엑셀에 적힌 값을 그대로 클릭합니다.

```python
for col in ["웹문서함1", "웹문서함2", "웹문서함3", "웹문서함4"]:
    folder_name = row[col]
    await page.get_by_text(folder_name, exact=True).click()
    await page.wait_for_load_state("networkidle")
```

사이트가 트리 구조라면 `get_by_text()` 대신 실제 CSS selector나 XPath를 씁니다.

**6. 업로드**

숨겨진 file input이 있으면 가장 안정적입니다.

```python
file_paths = [str(p) for p in files]

await page.set_input_files("input[type=file]", file_paths)
await page.wait_for_selector("text=업로드 완료")
```

정말 드래그 앤 드랍만 받는 구조라면 Playwright에서 drop 이벤트를 만들어 넣습니다.
하지만 대부분의 드래그 업로드 UI는 내부에 `input[type=file]`이 숨어 있어서 그걸 쓰는 게 안정적입니다.

**7. 결과 로그**

각 ID마다 기록합니다.

```python
log.append({
    "사용자ID": user_id,
    "로컬경로": str(local_dir),
    "파일수": len(files),
    "결과": "SUCCESS",
    "메시지": "",
})
```

실패하면:

```python
log.append({
    "사용자ID": user_id,
    "로컬경로": str(local_dir),
    "파일수": len(files),
    "결과": "FAILED",
    "메시지": str(e),
})
```

**8. 실행 모드**

최소 3개는 두는 게 좋습니다.

```bash
python run.py --excel upload_list.xlsx --mode dry-run
python run.py --excel upload_list.xlsx --mode run
python run.py --excel upload_list.xlsx --mode retry-failed
```

`dry-run`은 로그인, 경로 이동, 파일 목록 확인까지만 하고 업로드는 안 합니다.
`run`은 실제 업로드합니다.
`retry-failed`는 실패 로그에 있는 ID만 다시 처리합니다.

**최종 루틴**

```text
엑셀 행 읽기
→ 로컬 전체 경로 이동
→ 파일 목록 배열화
→ 해당 ID 로그인
→ 웹 문서함 4딥스 이동
→ 파일 업로드
→ 완료 확인
→ 로그 기록
→ 로그아웃
→ 다음 ID
```

이 방식으로 구현하면 하드코딩 없이 엑셀만 바꿔서 100명, 445개 문서 전체를 돌릴 수 있습니다.
